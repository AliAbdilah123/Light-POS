Scope and assumptions

Included

  • Upload, preview, replace, and remove one tenant QR.
  • Admin: own tenant only.
  • Superadmin: any explicitly selected tenant.
  • Cashier view during QRIS checkout.
  • PNG, JPEG, WebP; 2 MB maximum; signature verification.

Explicitly excluded

  • Dynamic QR generation.
  • Payment-provider confirmation.
  • Webhook settlement or reconciliation.
  • QR history/version restore.
  • Per-register QR unless requested.

Primary assumption: “Payment QR” means a static tenant-owned QR image. It is display-only and must never be presented as proof that payment settled.

Minimal architecture

Storage

A dedicated tenant_payment_qr SQLite table keyed by business_id, containing MIME, BLOB bytes, updater, and timestamp. This avoids polluting shared POS JSON state.

API

Metadata GET, authenticated image GET, raw-image PUT, and DELETE. Mutations require CSRF and Admin/Superadmin authorization. Image responses use nosniff and private caching.

Admin UI

Reuse the existing Admin shell, tenant selector, PageHead, cards, buttons, alerts, and navigation. Aggregate all disables configuration with a tenant-selection instruction.

Checkout UI

QRIS shows only the active tenant image. Cash remains unchanged. Missing configuration has an explicit unavailable state and must not falsely confirm payment.

Implementation tasks

  1. Storage and validators: schema plus PNG/JPEG/WebP signature, MIME, empty, and 2 MB checks in server/app.mjs; backend tests first.
  2. Secure endpoints: role/scope matrix, CSRF, upload/replace/read/delete, response headers, and audit entries; test every denied role and cross-tenant call.
  3. Admin settings page: add src/pages/AdminPaymentQrPage.tsx, route/nav, accessible upload/preview/replace/remove states, and selected-tenant guard.
  4. QRIS checkout: extend the existing payment surface in src/pages/OrderEntry.tsx; display active tenant QR without changing settlement semantics.
  5. Verification and delivery: changelog/feature ledger, full frontend/backend/typecheck/lint/build, restart, deploy, then public E2E with Admin, Superadmin, Manager, and Cashier sessions.

Expected checks: npm test, npm run test:backend, npm run typecheck, npm run lint, npm run build, and npm run test:e2e:public.

Acceptance criteria

  • Tenant QR data cannot leak across tenants.
  • Own-tenant Admin and selected-tenant Superadmin can persistently upload, replace, and remove.
  • Other roles and cross-tenant calls receive HTTP 403, including direct API attempts.
  • Spoofed/oversized/unsupported files are rejected before storage.
  • Superadmin cannot mutate in aggregate all mode.
  • Checkout displays the QR only for QRIS and never labels a static image as verified payment.
  • Changelog is updated; deployed public E2E passes before READY.

Open questions for approval

  1. Confirm this is a static uploaded QR image, not provider-generated dynamic QRIS.
  2. Should checkout block QRIS completion when no tenant QR is configured, or allow an external/offline QR?
  3. Is one QR per tenant sufficient, or is one QR per outlet/register required?

Implementation gate

This is a review plan only. Answering the questions or approving the plan does not authorize implementation or deployment. Work starts only after an explicit instruction to implement.
