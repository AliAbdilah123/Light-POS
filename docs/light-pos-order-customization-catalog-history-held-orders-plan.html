LIGHT POS · IMPLEMENTATION REVIEW

Ordering, catalog history & held orders

A minimal, sequential plan using existing React, store, modal, and test infrastructure.

Problems captured

  1. All New Order menu clicks need customization, including notes.
  2. Line editing must look and behave exactly like add customization.
  3. Catalog needs cleaner button labels, historical version viewing, safe archive confirmation, and an archive filter defaulting to active menus.
  4. Held orders need a count-driven picker and safe state replacement confirmation.

Current code evidence

  • OrderEntry.tsx customizes only menus with variations; plain items add immediately.
  • Line editing currently exposes only note/modifier and does not mirror add customization.
  • Held-order header resumes only the first held order and uses window.confirm.
  • AdminMenuPage.tsx owns menu versions and archive state.
  • The domain already has menu versions, archived state, and cart-line notes—no expected schema work.

Interpretation: clicking a catalog card opens read-only historical versions; explicit Edit/Archive actions remain separate. Button labels lose “version”, while history metadata retains version numbers.

Ordered tasks

1 · Failing interaction tests

Cover universal customization, note persistence, identical edit behavior, filters/history, archive confirmation, and every held-order restore/cancel branch. Verify RED first.

2 · Shared add/edit customization

Use one form path for variations, quantity, notes, price, and contextual submission. Preserve long-press details and unavailable behavior. Run focused and full tests before continuing.

3 · Catalog filter and history

Add Active / Archived / All (default Active), remove “version” from action buttons, and open a newest-first read-only history modal from card click.

4 · Destructive confirmation

Use the existing accessible Modal for named Archive confirmation. Cancel is mutation-free; confirm archives once.

5 · Held-order picker

Show only the count in the header. List every held order in a modal. Restore directly when empty; otherwise confirm replacement in-app, then close dialogs.

6 · Build, authenticated public E2E, finalize

Run test, lint, typecheck, build; deploy through the discovered Light POS path; verify desktop/mobile, reload persistence, keyboard modal behavior, and console cleanliness. Then commit and push.

Verification ladder

  1. npm test -- --run
  2. npm run lint
  3. npm run typecheck
  4. npm run build
  5. Authenticated public Playwright E2E for all requested flows

No task starts until the previous task is green. READY only follows public E2E.

Minimal scope

Likely changes: OrderEntry.tsx, AdminMenuPage.tsx, App.test.tsx, minimal CSS, and store.tsx only if atomic line editing is missing. No dependencies, backend, rollback UI, or generalized framework.

Implementation Gate

Plan approval is not implementation permission. Work starts only after an explicit instruction to proceed. Implementation will use Codex gpt-5.6-sol, medium, on a new feature branch.
