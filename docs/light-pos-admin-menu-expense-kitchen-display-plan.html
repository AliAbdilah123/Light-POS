Current evidence

  • Frontend-only React/Vite demo with one localStorage aggregate.
  • Roles, service modes, menu, and tables are currently hard-coded.
  • Role switching is navigation/UI behavior, not authorization.
  • Expenses currently have only label, amount, and date.
  • No Git remote is configured, so final push currently has no destination.
Scope posture: produce the smallest truthful extension of this demo. Do not imply secure permissions, private OCR, or cross-device kitchen synchronization without a backend.

Proposed model

Persist and migrate OrderType, Seat, versioned MenuItem/MenuVersion, one-level ExpenseLine, and Experiment. Historical orders remain immutable snapshots. Referenced entities archive rather than disappear.

  • Ingredients default hidden: true.
  • Bundles contain standard menu IDs + quantities and a custom price.
  • One experiment can be active; finalize is idempotent and creates menu versions.
  • Admin receives the capability union; Kitchen and Display remain least-privileged.

Ordered milestones

1 · Dashboard cleanup

RED→GREEN test, then remove only the Shift sales metric.

2 · Configurable order types

Seed Dine In, Takeaway, Delivery. Admin add/enable/disable/archive. New Order renders only enabled types and uses a requiresSeat flag.

3 · Managed seats/tables

Persist add/edit/archive/status/capacity. Protect active-order references and drive New Order choices from live state.

4 · Detailed expenses

Historical searchable categories, one nested line-item level, derived totals, inclusive date range, and removal of Recorded badges.

5 · Receipt prefill

Validate image, parse through an approved provider boundary, prefill editable fields, never auto-save or persist image bytes.

6 · Admin capability union

Central capability helper and reused cashier/manager pages; no duplicate implementations.

7 · Versioned menu + ingredient privacy

Create/edit-as-version/archive; long-press plus keyboard-accessible detail; expose only non-hidden ingredients.

8 · Bundle menu

At least two standard components, no cycles, custom price, immutable checkout snapshot.

9 · Experiments

Assumptions, menu drafts, daily targets, deterministic revenue/ingredient projections, one-active invariant, confirmed idempotent finalize.

10 · Kitchen role

Oldest-first Preparing cards, full-screen details, mark Ready, and set menu available/low/sold-out.

11 · Display role

Read-only current menu for the selected operational scope, with hidden ingredients excluded.

12 · Integrated delivery

Full tests, responsive role-matrix browser E2E, commit, push after remote exists, and deploy only after explicit instruction.

Verification gates

  1. Exactly one milestone active at a time; stop on any failure.
  2. Focused behavior test first, then npm test, lint, typecheck, build.
  3. Final base-path build: npm run build -- --base=/projects/light-pos/.
  4. Browser matrix at 320, 375, 414, 768, and 1024 px with no overflow or runtime errors.
  5. Reload persistence and admin/cashier/kitchen/display behavior matrix.

Risks and tradeoffs

  • Local storage does not synchronize roles across devices.
  • Client role checks are not security controls.
  • Receipt images are private and must not carry secrets through a browser-embedded API key.
  • Legacy local data needs explicit migration tests.
  • Experiment outputs are scenario arithmetic, not causal predictions.

Confirmed decisions · 12 Sep 2026

  1. The backend owns OCR/vision and stores receipts; no provider credential enters the frontend.
  2. Manage tables, grouped by capacity availability such as 2 seats: 2/5; dine-in orders may select multiple tables.
  3. Archive is preferred for historically referenced records.
  4. Display shows prices and uses the active experiment menu set for the current app session, otherwise the default menu.
  5. Kitchen lists Preparing orders only.
  6. Finalizing an experiment applies it to the main menu immediately.
