Confirmed direction

  • Feature enablement and menu scope become one Access Profile.
  • Do not expose separate editable Role and Group concepts.
  • Current roles become protected system profiles; admins duplicate them into editable tenant profiles.
  • Each user gets one profile. Existing users migrate automatically with unchanged behavior.
  • Menu scope supports both categories and individual items using union semantics.

Users & access

The administration page has two tabs: Users and Access profiles. User editing assigns one profile instead of separate role and group fields.

Profile editor
  1. Details: name and source system profile.
  2. Enabled features grouped by Orders, People, Operations, Catalog, Reporting, and Administration.
  3. Menu access: All menu or Limited menu with categories and searchable items.

System profiles are viewable and duplicable, but cannot be edited or deleted.

Merge with current roles

Recommended model: Access Profiles

The existing role/capability implementation is the seed, not a separate layer. Roles become immutable system profiles; custom profiles use the same stable capability keys plus resource scope.

Current conceptUnified model
RoleProtected system access profile
CapabilityStable feature key assigned to profiles
Server MUTABLE mapBackend action policies tied to capabilities
GroupNot separate; replaced by custom access profile

Global Superadmin remains reserved. Tenant admins cannot grant global, cross-tenant, or reserved access-profile administration powers.

Enforcement rules

AreaRule
Effective accessRequires both the relevant enabled feature and applicable resource scope.
MenuSelected category OR selected item; empty limited scope means no menu access.
BundlesBundle and every required component must be accessible.
BackendRoutes, reads, and mutations enforce capabilities; order lines enforce menu scope.
NavigationGenerated or filtered from effective capabilities; direct routes use the same checks.
SessionsProfile edits revoke/refresh affected active sessions immediately.
DeletionAssigned users must be reassigned before custom-profile deletion.

Implementation sequence

  1. Tests first: capability allowlists, role parity, menu unions, empty scope, bundles, and crafted denied requests.
  2. Persistence: access profiles, feature grants, category/item scope, and user profile assignment. Migrate current roles to protected profiles.
  3. API: list/create/duplicate/update/delete profiles; validate dependencies and reserved powers.
  4. Session and authorization: return effective capabilities/scope and replace role-only endpoint checks.
  5. Users & access UI: grouped feature checkboxes, menu selectors, assignments, responsive/accessibility states.
  6. Order entry: apply scope before search/detail/customization/held-order and bundle flows.
  7. Delivery: changelog, complete tests/lint/typecheck/build, push, restart/deploy, and public E2E.
Public E2E scenario

Duplicate Cashier into “Food Cashier,” disable unrelated features, allow a food category plus one out-of-category item, assign a user, then verify enabled/disabled navigation, permitted products, denied products, and server rejection of a crafted unauthorized order.

MVP limits

  • One access profile per user.
  • No per-user overrides, multi-profile composition, or field-level permissions.
  • No scheduled or sub-location scope.

Implementation gate

Review only.

No implementation, deployment, or production migration until Capt4ce explicitly approves implementation.
