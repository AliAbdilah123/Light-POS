LIGHT POS / REVIEW
Implementation plan · 24 November 2026

Offline first, without silent data loss.

Native app-shell caching, durable tenant snapshots, and an idempotent mutation outbox. The first release detects concurrent changes instead of pretending it can safely merge every POS workflow.

Implementation gate: review only. No production code, deploy, commit, or push begins until Capt4ce explicitly approves.

Current evidence

  • src/store.tsx reads state then writes a complete tenant snapshot guarded by one revision.
  • A failed write reloads server state and discards the optimistic local result.
  • There is no service worker, manifest, IndexedDB store, or durable outbox.
  • Replaying an old whole-state snapshot could overwrite another terminal’s sales; caching alone is unsafe.
  • Deployment scope is /projects/light-pos/, which the service worker must preserve.

Scope and defaults

  • Offline use requires one successful prior sign-in on that device.
  • Tenant operational state and safe mutations work offline.
  • Login, administration, uploads, OCR, network printing, and password changes remain online-only.
  • Data is isolated by user + tenant and purged on logout.
  • Conflicts are retained for explicit resolution—never silently overwritten.
  • No new npm dependency.

Verify and release

All checks, clean build/deploy, service restart, public desktop/mobile E2E for offline reload, durable queued sale, reconnect, duplicate replay, and two-terminal conflict. Then changelog, commit, and push.

Acceptance criteria

  • Previously authenticated operators can reload cached tenant state without network.
  • Offline mutations survive browser reload and remain visibly pending.
  • Reconnect applies each operation once; duplicate delivery is harmless.
  • Concurrent revisions produce visible conflicts without overwriting either version.
  • Cached data cannot cross user or tenant boundaries.
  • API responses and credentials never enter Cache Storage.
  • Online-only controls are clearly unavailable offline.
  • Automated checks and public offline/reconnect E2E pass.

Deliberate V1 ceiling

ponytail: queue revision-guarded tenant snapshots first. This safely supports one offline writer and detects multi-terminal conflicts. Add domain merges—append-only orders, inventory deltas, table transitions—only when conflict telemetry justifies them.

Risks

  • Busy multi-terminal tenants may see frequent conflicts; V1 detects rather than guesses.
  • POS data cached on-device is sensitive; namespacing and logout purge are mandatory.
  • Service-worker cache upgrades need real update-path testing to prevent mixed assets.
