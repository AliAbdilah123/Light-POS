Executive recommendation

Keep the first release narrow and recoverable

Use a dedicated importer on /admin/menu. Upload up to five photos, extract strict structured drafts on the backend, let the admin edit every row, then save all accepted rows transactionally.

Do not auto-save, overwrite existing menus, or infer recipes, costs, bundles, variations, or ingredients in MVP.

Three explicit steps

01 · UploadJPEG, PNG, or WebP with visible limits and per-file feedback.
02 · ReviewEdit name, description, category, and price. Add missed rows or remove bad ones.
03 · SaveConfirm tenant and count. Create all rows or none.

What already exists

  • AdminMenuPage.tsx already creates versioned items and validates catalog fields.
  • domain.ts defines immutable MenuVersion and MenuItem.
  • app.mjs already enforces tenant access, CSRF, capabilities, revisions, transactions, and audit events.
  • receiptUpload.mjs already provides the security pattern for bounded multipart images, MIME/magic validation, parser isolation, and strict output validation.

Backend boundaries

POST /api/ai/menu-parsing

Authenticated multipart upload with CSRF, manageCatalog, tenant access, file limits, real image signature checks, bounded Hermes timeout, and strict JSON validation. Hermes uses backend-only HERMES_URL and HERMES_SECRET; neither value reaches the client, logs, state, or audit events.

POST /api/menu

Accepts an array: one element creates one menu and multiple elements create menus in bulk. It revalidates tenant access, every edited row, and duplicates, then appends version-1 menu items, increments state revision, and writes one audit event in one SQLite transaction.

Invariant: failed validation or persistence creates zero menu items.

Review experience

  • Secondary Import from photos action on Menu catalog.
  • Accessible picker and drag/drop, thumbnail/name/size, keyboard remove controls.
  • Processing state keeps filenames visible and prevents duplicate requests.
  • Desktop editable table; mobile stacked cards.
  • Existing category suggestions remain editable text—no new category model.
  • Exact normalized-name matches are highlighted and must be renamed or removed.
  • Save failures preserve all edits. Success reloads the catalog and shows a notice.
  • A stale extraction response cannot replace a newer selection.

Implementation sequence

  1. Validators: create server/menuImport.mjs and focused tests for files, provider schema, limits, and IDR normalization.
  2. Hermes adapter: use backend-only HERMES_URL and HERMES_SECRET, bounded timeout, normalized errors, and no secret leakage or mock success.
  3. Parsing route: implement POST /api/ai/menu-parsing with auth, CSRF, capability, tenant, multipart, provider failures, and strict output validation.
  4. Menu route: implement array-based POST /api/menu for atomic single and bulk creation, revision/concurrency checks, and audit.
  5. Frontend: add MenuPhotoImport.tsx, minimally integrate into AdminMenuPage.tsx, reuse existing controls/tokens.
  6. Save/recovery: confirmation, CSRF commit, state reload, retained edits on error.
  7. Verify and release: documentation, CHANGELOG.md, unit/backend/type/lint/build, restart/deploy, then public E2E.

Key acceptance checks

  • Correct one extracted price, save, refresh, and see every approved item.
  • Multiple photos keep source labels and submit only once.
  • Blurry/no-result images never alter the catalog.
  • Spoofed MIME, oversize, timeout, unavailable provider, and malformed AI JSON fail safely.
  • Cross-tenant parsing and menu creation are denied.
  • Duplicate names cannot overwrite existing menus.
  • Menu creation failure is all-or-nothing and preserves frontend edits.
  • A one-element array creates one menu; a larger array creates many atomically.
  • Images, HERMES_URL, and HERMES_SECRET never enter catalog state, logs, audit text, or client config.

Risks and deliberate cuts

OCR ambiguityMandatory human review and row warnings.
Provider latencyBound timeout/input. Add durable async jobs only if observed latency requires them.
Duplicate detectionExact normalized names only; fuzzy matching risks false positives.
Image privacyNo retention in MVP. Add only with explicit policy and deletion rules.

Open questions for approval

  1. Multiple photos up to five (recommended), or exactly one per import?
  2. Block exact duplicate names (recommended), or allow after explicit confirmation?
  3. When a description is not printed, leave it blank (recommended), or ask AI to generate one?

Implementation gate

This is a review plan only. No app code, database migration, deployment, or production behavior should change until implementation is explicitly approved. Answering the questions above updates the plan; it does not authorize deployment.
