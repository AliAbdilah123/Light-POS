# Light POS Offline-First Implementation Plan

> **For Hermes:** Implement this plan task-by-task with strict TDD after explicit approval.

**Goal:** Keep the installed Light POS shell usable without connectivity, preserve authenticated tenant data locally, queue safe mutations, and synchronize them without silently losing another terminal’s changes.

**Architecture:** Use native browser APIs only: a service worker/Cache Storage for the app shell and IndexedDB for tenant snapshots plus an ordered mutation outbox. Replace offline whole-state PUT replay with operation records carrying stable IDs and idempotency keys; the server applies each operation transactionally and reports accepted/conflicting operations. Existing online behavior and authorization remain authoritative.

**Tech Stack:** React 18, TypeScript, Vite, native Service Worker/Cache Storage/IndexedDB, Node HTTP, SQLite.

---

## Current evidence

- `src/store.tsx` loads `/api/session`, `/api/tenants`, and `/api/state`, then writes the complete tenant state through revision-guarded `PUT /api/state`.
- A failed write currently reloads server state, which discards the optimistic local result; there is no durable outbox.
- A replayed stale whole-state snapshot would overwrite unrelated sales after reconnection, so caching alone is not sufficient.
- The project has no service worker, web manifest, IndexedDB store, or online/offline status UI.
- The app is deployed under `/projects/light-pos/`; service-worker scope and cache URLs must honor `BASE_URL`.

## Confirmed scope / defaults

1. Offline access is for a user who has signed in successfully on that device before.
2. Offline mode covers tenant operational state and safe state mutations; login, logout, tenant/user administration, uploads, receipt OCR, network printing, and password changes remain online-only.
3. Cached data is isolated by user ID and tenant ID. Logout removes cached session/data/outbox for that user.
4. The server remains authoritative. Conflicts are retained and shown for explicit resolution; they are never silently dropped or overwritten.
5. No new npm dependency.

## Ordered implementation plan

### 1. Define and test the sync contract

**Files:**
- Create: `src/offline.test.ts`
- Create: `src/offline.ts`
- Modify: `src/store.tsx`
- Modify: `server/app.node.test.mjs`
- Modify: `server/app.mjs`

Write failing tests for stable mutation IDs, ordered replay, duplicate replay idempotency, tenant/user isolation, stale-base conflicts, and rejection of unauthorized operations. Define the smallest operation envelope: `{id, userId, business, baseRevision, action, createdAt, data}` for V1. The full snapshot stays in each queued operation initially, but the server accepts it only when its base revision still matches; this guarantees no silent overwrite and provides a safe ceiling for later domain-level merge operations.

### 2. Add durable browser storage

**Files:**
- Create: `src/offline.ts`
- Test: `src/offline.test.ts`

Implement a tiny native IndexedDB wrapper with stores for `snapshots` and `outbox`, keyed by authenticated user + tenant. Cache only successful state responses. Persist an outbox item before considering an optimistic mutation durable. Add migration/version handling and explicit storage-error propagation.

### 3. Make boot and mutations offline-aware

**Files:**
- Modify: `src/store.tsx`
- Modify: `src/App.test.tsx`

On online boot, authenticate normally and refresh the cache. If session/state fetch fails because the network is unavailable, restore the last cached authenticated session and tenant snapshot. Queue writes while offline, preserve optimistic state, expose `online`, `pendingCount`, `syncing`, and `conflicts`, and retry on the browser `online` event plus a manual Sync action. Do not infer connectivity solely from `navigator.onLine`; failed/successful requests update effective status.

### 4. Add idempotent server synchronization

**Files:**
- Modify: `server/app.mjs`
- Modify: `server/app.node.test.mjs`

Add a SQLite `sync_operations` table with operation ID, actor, tenant, status, timestamps, and result revision. Add an authenticated + CSRF-protected sync endpoint that transactionally applies unseen operations in order. Duplicate IDs return their stored result. Stale revisions return a conflict with current server data and leave the operation unresolved. Existing mutation authorization and state validation remain mandatory.

### 5. Cache the application shell

## Acceptance criteria

- A previously authenticated operator can reload and use cached tenant state with the network disabled.
- An offline mutation survives page/browser reload and is visibly marked pending.
- Reconnection synchronizes each operation once; duplicate delivery is harmless.
- A concurrent server revision produces a visible conflict and never overwrites either version silently.
- Cached records are inaccessible across users/tenants and are removed on logout.
- API responses and credentials are not placed in Cache Storage.
- Unsupported online-only actions are clearly disabled offline.
- App shell updates activate predictably without serving mixed asset versions.
- All automated checks and public offline/reconnect E2E pass.

## Deliberate V1 ceiling

`ponytail:` V1 queues revision-guarded tenant snapshots rather than inventing a domain merge engine. This safely supports one offline writer and detects multi-terminal conflicts. Add operation-specific merges (orders append, inventory delta, table state transition) only after conflict telemetry proves they are needed.

## Risks

- Whole-state queued snapshots can conflict frequently on busy multi-terminal tenants; V1 detects rather than auto-merges.
- Cached POS data is device-local sensitive data. User/tenant namespacing and logout purge are mandatory; device-at-rest encryption is outside browser-only guarantees.
- Service-worker cache upgrades can strand old clients if versioning is wrong; public update-path E2E is required.
